# 검증 가이드

## 기본 원칙

변경 범위에 맞는 가장 작은 검증부터 실행하고, 완료 전에는 `npm run validate`로 CI 기준을 확인한다. 명령의 정의와 부작용은 `docs/COMMANDS.md`를 먼저 확인한다.

## 자동 검증

### 빠른 정적 검사

```text
npm run typecheck
npm run lint
npm run format:check
```

`format:check`는 포맷 검사지만 현재 `validate`에는 포함되지 않는다.

### 테스트

```text
npm run test
```

현재 확인된 테스트 영역은 다음과 같다.

- ALIO 상세 매핑
- Jooble 클라이언트
- 공고 어댑터·정규화·분석
- SQLite 저장과 파이프라인
- B2B 신호 분석
- 공통 Button
- 무료 체험 검색 UI와 오류 처리
- 콜드메일 신청 UI와 검증

### 빌드와 전체 검증

```text
npm run build
npm run validate
```

GitHub Actions의 CI는 Node 버전을 `.nvmrc`에서 읽고 `npm ci` 후 `npm run validate`를 실행한다.

## 수동 확인 흐름

UI 또는 검색 흐름을 변경한 경우 개발 서버에서 다음을 확인한다.

1. 랜딩에서 `/experience`로 이동한다.
2. 필수 역할과 목적이 없을 때 입력 오류가 표시되는지 확인한다.
3. 유효한 조건으로 검색해 `/experience/results`에 결과 또는 설명 가능한 오류가 표시되는지 확인한다.
4. 추천 카드에서 `/result/:companyId`로 이동하고 공고 근거와 분석이 전달되는지 확인한다.
5. 상세 화면에서 `/apply`로 이동해 대상 기업이 유지되는지 확인한다.
6. 신청 폼의 이메일, 회사명, 제품명, 제품 설명 길이, 정보 처리 동의를 검증한다.
7. 개발 환경에서 성공 상태에 Mock 접수 안내가 표시되는지 확인한다.

검색 수동 검증은 `data/job-signals.db`의 수집 데이터 또는 유효한 외부 API 키에 영향을 받는다. 실제 키나 원본 응답을 검증 기록에 남기지 않는다.

## 라우트 상태 확인

- `/experience/results`를 직접 열거나 새로고침했을 때 현재 구현은 `/experience`로 돌아갈 수 있다.
- `/result/:companyId`를 직접 열면 라우트 상태가 없어 fallback 분석을 사용할 수 있다.
- `/apply`를 직접 열면 개발 환경은 Mock 기업을 사용하지만 운영 환경은 대상 기업이 없다고 표시한다.

이 동작이 요구사항에 맞는지는 `확인 필요`이며, 검증 실패로 단정하지 않는다.

## 문서 전용 변경 검증

문서만 변경하는 작업에서는 최소한 다음을 확인한다.

- 변경 파일 목록이 요청된 Markdown 문서로 제한되는지
- 문서에 환경변수 값, 개인정보, 로컬 원본 데이터가 포함되지 않았는지
- 명령이 현재 `package.json`의 scripts와 일치하는지
- 경로와 라우트가 현재 작업 트리에 존재하는지
- 확인되지 않은 운영 규칙이 `확인 필요`로 표시되었는지

## 완료 기준

- 관련 자동 검증이 통과했거나 실행하지 못한 이유가 보고되어 있다.
- 수동 검증이 필요한 화면 흐름의 결과가 기록되어 있다.
- 코드, 데이터, 설정의 알려진 제한을 성공 동작으로 오해하지 않는다.
- `git status`와 diff로 의도하지 않은 파일 변경이 없는지 확인했다.
